# Bulk Job Applying on BOSS Zhipin（通用 Agent 版）

在使用者本人已登录的桌面浏览器上，按锁定三段式话术逐岗沟通投递 BOSS 直聘。
简历是唯一事实来源：先读 `resume/RESUME_SLOT.md` 登记的简历，未上传简历不得启动。

## Confirm the device and login before you start

- Run bulk applying only in the desktop browser on the device the user is messaging from.
- Treat a continue message sent from a phone as unable to control a desktop browser, and ask the user to send continue from the desktop device before you start.
- Stop rather than substitute a cloud browser or a mobile web version when the desktop browser is unavailable.
- Check that the browser shows the user logged in under the expected account before you send anything, and ask the user to log in on that device when the browser shows a login page.
- Read the online resume on that logged in account and compare its intent, education and work history with the uploaded baseline resume, and stop and reread the same page when any field does not match.
- Never schedule an unattended bulk applying run, and end a scheduled run at once when the browser is logged out instead of retrying it as if a login will appear.

## Lock the copy rules before the first send

- Use the three part form, with experience background first, project proof second and job matching third.
- Open without a greeting and without a stock opener, and start the first paragraph with the experience itself.
- Keep the whole message near 300 to 450 chars and keep the tone serious and professional throughout.
- Write concrete categories, duties, platforms and data from the baseline resume, and leave out empty praise and stock phrases.
- Vary the emphasis and matching angle for each job, and use only one or two numbers that fit that job.
- Keep participated, responsible and led wording exactly as the baseline resume states it, and never invent experience the resume does not list.
- Close the third paragraph with a statement that sells what the user can do, and never close with a question.
- Never open with 本人, and use the locked template opening for every message instead of rotating the opening sentence across jobs.
- Keep the three separate paragraphs when sending (never collapse the message into one block), keep the main line of the resume as the main line, and adapt mainly the job matching paragraph per job description. Never promote side skills into the main experience just to fit a job description, and never use a forced opening sentence to vary the wording.

## Run one job at a time and stop on a correction

- Follow the list order the user set, starting with the recommended list and moving to the target job list after about ten sends; in unlimited mode keep rotating until a stop condition hits.
- Apply no salary filter, and skip jobs already contacted, pure on camera hosting, pure sales or customer service, manager roles that require far more experience or team size than the resume shows, roles with a hard language requirement and roles whose hard threshold is experience the user does not have.
- Work one job at a time by reading the job description, writing the message for that job, sending it, confirming the sent state and then closing that job tab.
- Keep the main list page as the anchor for position continuity: open each job in a separate tab from that list, send the message there, close that tab and come back to the untouched list page. Never open a job in the list page itself and use back after sending: BOSS refreshes the list on return and the position is lost. If the list ever reloads to the top, skip the jobs already marked as contacted to pick up where the run left off.
- Never open the message inbox and never read or answer recruiter replies, since the user handles those.
- Stop the running batch at once when the user corrects the copy or the rules, and resume only after the user sends continue from the device that controls the browser.

## Report only what the browser confirmed

- Count only sends the browser confirmed as sent, and say plainly that a round total is unconfirmed when the browser has not reported it.
- Send no batch by batch report, and interrupt the user only for a platform limit, a verification challenge, a dropped login or a decision that needs the user.
- Tell the user at once when a send fails, and name the job and the reason the browser gave.
